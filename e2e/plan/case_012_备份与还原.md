# case_012 备份与还原（修订版）

> 本文件是 `case_012_备份与还原.md` 的修订版，记录并固化了与实测一致的计划内容；
> 修订点见文末「修订记录」。正式脚本：`e2e\script\case_012\case_012.js`。

## 测试主题

覆盖数据目录备份与还原全流程：备份对话框（数据目录大小显示、冗余比例修改、预计大小、进度阶段、成功提示与 `.ibackup` 产物）、还原探测（正常/存在损坏块/不可恢复三种结果）、确认还原与进度、还原成功对话框与页面刷新，以及还原后的数据回退验证。本用例验证「备份产物 → 探测分级 → 全量还原 → 数据恢复」链路。

## 前置条件

- 复制 fixture `base` 到 `<case>\output\data` 并以该目录启动应用
- **准备阶段向数据目录写入 64MiB 大附件**（`user_database_set\<id>\attachment\e2e-large-attachment.bin`）：
  放大备份/还原耗时，使界面的进度阶段具备可观察窗口（未登记的附件文件属于数据目录级全量备份的范围，不影响数据库内容断言）
- 解锁 `zz-e2e-base` / `e2e-password`，进入根画布后将「备注 B」改名为 `备注 B-备份前`，「保存并退出」回首页（保证备份时数据目录为已保存状态）
- 界面语言：中文
- 备份/还原入口均在首页右下角：`aria-label="备份数据目录"`、`aria-label="还原数据目录"`

## 覆盖范围

前端功能点：
- 备份对话框：「当前数据目录大小：{size}」显示、冗余比例数字输入（默认 0.05）、「预计备份大小：{size}」随比例变化、开始备份按钮可用态、FilePicker save（默认文件名 `backup.ibackup`）
- 备份进度：阶段文案与进度条（观察方式见「备注与风险」）、备份成功 snackbar「备份已保存」
- 还原对话框：警告文案、选择备份文件（FilePicker open、扩展名 ibackup）、探测结果三种展示、确认还原可用性、还原阶段文案与进度条
- 还原成功对话框：「还原成功」「点击下方按钮刷新页面以查看还原后的数据。」唯一「完成」按钮 → 页面刷新回首页
- 还原成功后前端依次调用三个 reclaim 接口（`reclaim_preference` / `reclaim_metadata` / `reclaim_user_database`，经「还原后重新解锁看到备份时点数据」间接验证）

后端命令（经由 UI 触发）：
- `backup_data_directory_size`（打开备份对话框时）
- `backup_backup`（含进度事件 `backup-progress`）
- `backup_restore_probe`（探测 `lost` 与 `recoverable`）
- `backup_restore`（含进度事件 `restore-progress`）
- `reclaim_preference`、`reclaim_metadata`、`reclaim_user_database`
- `file_system_list_directory` / `file_system_roots` / `file_system_path_exists`（文件选择器）

## 备注与风险

- 冗余比例后端要求开区间 (0, 1)，输入 0 会触发 `InvalidBackupFile`；前端 `min=0.01` 仅约束步进控件，不阻止提交。
- 备份文件体积约为数据目录的 (1 + 冗余比例) 倍；数据目录大小含 `metadata.sqlite`、`preference.sqlite`、
  `user_database_set\`，**不含** `logs\`（打包时跳过日志）。实测 64MiB 数据目录在 0.1 比例下产物约 1.06 倍
  （tar 头与 shard 补齐开销小于冗余块开销）。
- 还原会覆盖数据目录但保留 `logs\`；还原完成后必须依靠前端三个 reclaim 接口刷新内存连接，
  否则会使用陈旧内存连接（本用例通过「还原后重新解锁看到旧数据」间接验证 reclaim 生效）。
- 探测结果为「存在损坏块仍可还原」的场景需要构造「损坏数 ≤ 冗余块数」的备份；本用例只覆盖两端
  （通过 / 不可恢复），中间态记录为可选扩展。
- **进度阶段的观察方式（2026-09-21 修复后）**：备份类命令已改为异步 Tauri 命令，
  `/ui-tree` 与 `/screenshot` 在业务进行中保持可用；脚本以 150ms 间隔直接轮询，断言出现首阶段
  （备份「正在打包数据目录」/ 还原「正在读取文件头」）、阶段为预期顺序的有序子集、结束停在最后阶段，
  并断言业务期间接口可用性（每轮 `/ui-tree` 全部成功且无 5xx、单轮耗时 < 3000ms、
  `/screenshot` 单张耗时 < 3000ms、探测轮次 ≥ 10；见修订记录第 12 条）。此前的阻塞现象与
  并发探测池应对方案见修订记录第 13 条。
- 还原成功后的「完成」按钮执行整页 reload（`window.location.replace("/")`），脚本等待
  「还原成功」消失且首页「数据库名称」输入框出现后再继续。
- 比例输入框的 `min`/`max` 属性不在 UI 树属性白名单内，无法断言（仅断言 `type=number` 与默认值）。
- 本用例不覆盖应用退出触发的中断还原场景。

## 修订记录

1. **准备阶段新增 64MiB 大附件**：原计划未提供放大数据的手段；实测 fixture 数据（164KB）下备份在
   秒级内完成、进度阶段与事件洪峰重叠导致外部无法观察。改为在数据目录 attachment 下写入 64MiB
   附件（属数据目录全量备份范围），使备份/还原的业务阶段有秒级窗口；数据目录大小断言、备份文件
   大小断言与预计大小断言均按含附件的实际值核算。
2. **步骤 4/10 的阶段断言口径**：原计划「依次出现阶段文案（至少出现首阶段与结束态）」不可稳定
   满足——实测事件洪峰期间 `/ui-tree` 与 `/screenshot` 请求被排队（最长达 10 秒超时），中间阶段
   无法通过串行轮询捕捉（探索实验中 backup 与 restore 各只捕捉到最后阶段）。修订为并发探测池的
   「至少一个阶段、有序子集、结束停留在最后阶段」硬断言 + 进度截图留档；首阶段/中间阶段的完整
   序列由后端单测覆盖，并新增「疑似性能观察」上报（见备注与风险）。
3. **步骤 1 的目录大小断言**：新增「UI 文本数值与脚本按同口径（递归非 logs 文件）统计值一致（±1%）」。
4. **步骤 1 的输入框属性断言**：`min`/`max` 不在 UI 树属性白名单内，改为断言 `type=number` 与默认值
   0.05（剪贴板）；「前端 min 不阻止提交 0」的行为由 F1 覆盖。
5. **步骤 5 的大小上限**：新增「≤ 1.5 倍」上限断言（原计划仅要求 ≥ 原大小）；实测 1.06 倍。
6. **步骤 11 的按钮断言**：明确「恰有一个子树文本为『完成』的按钮」（按 role=button 计数）。
7. **步骤 12 的等待方式**：明确等待「还原成功」消失且首页名称输入框出现（整页 reload）。
8. **F3 偏差固化**：文件选择器对非 `.ibackup` 文件默认过滤、开启「显示全部文件」后置灰不可选中，
   原计划预期的探测失败请求在 UI 上不可达；按原计划授权记录偏差，断言改为验证过滤阻止行为
   （默认不可见、确认禁用、单击不选中、双击不关闭）。
9. **新增 F6**：追加伪 `.ibackup`（内容非法）失败路径，有效覆盖 F3 意图中的「探测失败」路径。
10. **F4/F5**：按原计划不构造，仅记录（F5 破坏性、F4 文件选择器默认路径不指向数据目录）。
11. **探测等待超时**：正常/损坏探测均为秒级（64MiB 备份下 1~3 秒），等待超时取 60 秒以容忍磁盘波动。
12. **进度阶段断言升级（修复追溯，2026-09-21）**：应用修复（2026-09-21）第 4 条（原「备份/还原期间接口被阻塞」问题）已落地——4 个备份类命令
    （`backup_backup`、`backup_restore`、`backup_restore_probe`、`backup_data_directory_size`）改为
    异步 Tauri 命令，业务执行不再占用 WebView2 IPC 主线程（修复验证：备份全程 13.4 秒内 13 轮
    并发探测全部 200 且低于 3 秒，`/ui-tree` 6–9ms、`/screenshot` 674–766ms）。脚本据此把
    「并发探测池（fire-and-forget）」改为**固定间隔直接轮询**（150ms）：备份断言出现首阶段
    「正在打包数据目录」、还原断言出现首阶段「正在读取文件头」，保留「有序子集」与「结束停在
    最后阶段」断言；每个观察到的阶段留档一张截图（`progress-<kind>-stage<N>.png`）与结束态截图
    （`progress-<kind>-end.png`）。新增「业务进行中调试自动化接口保持可用」断言：每轮 `/ui-tree`
    全部成功且无 5xx、单轮耗时 < 3000ms、`/screenshot` 单张耗时 < 3000ms、探测轮次 ≥ 10
    （阈值取 3000ms，为修复记录实测值的约 4 倍余量）。
13. **首阶段可见性实测与参数修正（2026-09-21 追加）**：异步化后进一步实测，直接轮询下
    「某种阶段文案是否出现」取决于该阶段在 DOM 中的可见窗口，而非接口是否可用：
    - **备份「正在打包数据目录」**：64MiB 单文件附件下该阶段业务仅数十毫秒、UI 可见窗口低于
      一帧，不可稳定观察；数据目录追加 **6000 个 8KiB 小文件**（附件的 `bulk` 子目录）放大 tar
      打包的事件密度后，窗口约 469ms（+182ms→+651ms），以 **50ms 间隔**轮询可稳定捕捉 →
      首阶段硬断言成立；小文件群同时纳入数据目录大小、备份产物大小与还原恢复断言。
    - **还原「正在读取文件头」**：read_header 的业务耗时低于 1ms，两次阶段事件背靠背到达被
      前端批处理渲染合并，「正在纠错解码」（无损坏时）同样不进入 DOM；连续轮询实测（1665 轮、
      约 11ms 间隔、覆盖点击前后）从未在 UI 树中出现。脚本改为分支断言：观察到时按首阶段硬断言；
      未观察到时断言「最早可观察阶段为紧随的『正在校验完整性』」。若要硬断言首阶段，需应用侧为
      该阶段保证最小展示时长（建议 ≥ 100ms）。
    - 轮询间隔由 150ms 调整为 **50ms**；阶段截图改为**异步触发**（不阻塞轮询，避免截图耗时
      ~0.7 秒覆盖紧随的短阶段）；探测轮次下限由 10 调整为 **50**。
    - 数据放大后各阶段窗口充裕（verify 约 8.9s、unpack 约 3.4s、clear 约 0.5s、move 约 4.3s；
      备份 pack 约 0.4s、encode 约 10.7s、write 约 5.3s）。
